# Threat Model: OWASP CTF @ DEF CON 34 contestant web app (ctf-owasp-org)

## 1. System context

`ctf-owasp-org` is the contestant-facing web application for the OWASP Capture The Flag competition at DEF CON 34 (August 7–9, 2026, Las Vegas Convention Center). It is a Next.js 16 App Router application written in TypeScript (roughly 60 non-test source files plus a vitest suite), styled with Tailwind 4, package-managed with pnpm, and deployed on Vercel. Contestants sign in with GitHub through better-auth, then patch real vulnerabilities in six deliberately-insecure OWASP training apps — Juice Shop, DVWA, WebGoat, Security Shepherd, VulnerableApp, and VAmPI — and submit each fix as a pull request. Scoring happens entirely outside this repository: a CI scorer in the `dc34-owasp-secure-development-ctf` repo validates each patch and writes standings to Upstash Redis and a shared DynamoDB table. This application reads those standings and renders them; it has no write path to a score.

The app does own four pieces of mutable state: team membership (teams of up to four, enforced atomically), paid hints (a flat −10 point penalty per reveal, charged idempotently), a per-IP brute-force throttle for the pre-event access gate, and stateless session cookies. A fifth — an aggregate per-country visit counter — exists in the working tree but is not yet committed. Persistence is swappable at deploy time: `LEADERBOARD_SOURCE` selects mock/lambda/upstash/dynamo for reads, and `CTF_DATA_BACKEND` selects upstash/dual/dynamo for team and hint writes, with the codebase mid-migration from Upstash to DynamoDB. Authentication is stateless — better-auth is configured with no database, so sessions live entirely in JWE cookies keyed by `BETTER_AUTH_SECRET`. AWS access uses no stored keys: Vercel mints an OIDC token per deployment and exchanges it for the `ctf-web-dynamodb` IAM role in account 942548380662 (us-west-2), whose trust policy and table permissions are defined in a different repository.

Three properties of the deployment shape the threat picture more than any single code path. The audience is several thousand security professionals with both the skill and the incentive to probe the scoreboard. The event window is three fixed days, so an outage cannot be made up and a mid-event compromise cannot be quietly rolled back. And every security-relevant switch in the system — the hint economy, team writes, the pre-event gate, the data backend — is an environment variable read at module load, changeable only by redeploying.

## 2. Assets

| asset | description | sensitivity |
|---|---|---|
| Application secrets | `BETTER_AUTH_SECRET`, `GITHUB_CLIENT_SECRET`, the Upstash read/write token, and `CHALLENGES_GATE_PASSWORD`. Held only in Vercel environment variables and a local `.env.local` (gitignored and untracked — verified). `BETTER_AUTH_SECRET` is doubly load-bearing: session crypto and the gate cookie HMAC. | critical |
| Competition integrity | Leaderboard scores, ranks, and per-app solve counts. The reason the event exists. Owned by the external scorer; this app reads it, overlays hint penalties, and re-ranks. A forged or visibly wrong standing is unrecoverable reputationally mid-event. | high |
| Hint economy ledger | `HINTSPEND` items and `ctf:hints:spent`, plus one item per purchase. Written by this app and never rewritten by the scorer, so it is a live write path into displayed scores. | high |
| Contestant identity and session cookies | GitHub logins plus stateless JWE session cookies. The GitHub login is the primary key for scores, hints, and team membership. No session table exists, so there is no per-user server-side revocation. | high |
| Shared `ctf-leaderboard` DynamoDB table | Co-owned with the scorer, including the scorer-owned `LEADERBOARD` and `AUTHOR#` partitions. The webapp's IAM role reaches the table, not merely the partitions the webapp writes. | high |
| Site availability during the event window | A three-day fixed-date competition. An outage during DEF CON cannot be made up, and the leaderboard is the event's only feedback loop for contestants. | high |
| Hint text | Scorer-seeded solution hints in the Upstash `hints:<app>` hashes and DynamoDB `pk=HINTS`. Free or pre-event access converts directly into competitive advantage. | medium |
| Team membership records | Team name, slug, captain, and members, capped at four. Feeds public team standings; names are free text rendered publicly. | medium |
| Contestant IP addresses | Written into DynamoDB `pk=GATE` throttle items on every failed gate attempt. Retention depends on a `ttl` attribute that only functions if TTL is enabled on the table. | medium |
| Pre-event embargo on the challenge board | The `/challenges` catalogue is deliberately hidden until the conference starts. Early disclosure leaks the shape of the competition. | low |

## 5. Deprioritized

| threat | reason |
|---|---|
| Cross-site request forgery against the JSON POST routes | Session and gate cookies are `SameSite=Lax`, which blocks cookie attachment on cross-site POST, and every mutating route requires a JSON body. Revisit if `SameSite` is ever relaxed to `None` or a form-encoded route is added. |
| Stored XSS via team names, logins, or catalogue text on public pages | All rendering goes through JSX text children, which React escapes, and there is no `dangerouslySetInnerHTML` anywhere in `src/` (verified by grep). The residual risk is offensive content, not script execution, and is tracked as T14. |
| Command injection into Redis | Commands are built as positional arrays posted to the REST pipeline, Lua scripts are module constants taking `KEYS` and `ARGV` positionally, and challenge ids are regex-validated. No user input is concatenated into a command or a script body. |
| NoSQL injection into DynamoDB expressions | Every expression uses `ExpressionAttributeNames` and `ExpressionAttributeValues` placeholders; no user input reaches an expression string. Key components are validated (app enum, challenge-id regex, slugified team names, ISO-3166 country regex). |
| Spoofing the /profile gate by forging a session cookie | The proxy check is deliberately an optimistic cookie-presence test and the page re-verifies with `auth.api.getSession()`. A forged cookie earns a redirect, not data. Documented as intentional in `src/proxy.ts:17-19`. |
| Double-charging a hint, or racing past the four-player team cap | Both invariants are enforced atomically — a single Redis Lua `EVAL` or a two-entry DynamoDB `TransactWriteItems` with conditional guards — and both are covered by unit and live-integration tests. |
| Secrets committed to the repository | Verified: `.env*` is gitignored except `.env.example`, `.env.local` is untracked, `.env.example` holds empty placeholders only, and no credential literals appear in `src/` or `scripts/`. The AWS role ARN and table name in `src/lib/dynamo.ts` are identifiers, not secrets. |
| Repudiation on read-only pages | `/leaderboard`, `/challenges`, `/faq` and the policy pages change no multi-user state, so there is nothing to attribute. Repudiation is tracked only where points move, as T13. |
| Client-supplied geolocation poisoning the reach counters | `src/app/api/stats/visit/route.ts` reads the country only from the Vercel edge header, never the request body, and `normalizeCountry` rejects anything that is not ISO-3166 alpha-2 before it becomes a sort key. The counters carry no login, IP, or timestamp. The write-amplification half of this endpoint is tracked as T4. |
| Elevation of privilege to an administrative role | The application has no admin role, no privileged UI, and no server-side write path to scores. Scoring authority lives entirely in the external scorer, so there is no in-app privilege to escalate to. |

## 6. Open questions

Bootstrap mode derived this model from code, git history, and public advisories alone. The following need an owner:

- **Can any better-auth route set `user.login` from client input?** The comment at `src/lib/auth.ts:33-41` asserts that `input: true` is required for OAuth mapping and that nothing else can set the field. That assertion needs verifying against the installed better-auth version's actual route table, because `login` is the primary key for scores, hint spend, and team membership. This is the single highest-value question in the model (T1).
- **What exactly does the `ctf-web-dynamodb` IAM policy grant?** The trust policy and table policy live in the dc34 repo's `terraform/vercel-aws.tf`, so this repository's reviews never see them. Is the policy scoped with a `dynamodb:LeadingKeys` condition to the app's own partitions? Does the trust really cover preview deployments, and do previews point at the production table (T2)?
- **Is DynamoDB TTL enabled on the `ttl` attribute of `ctf-leaderboard`?** The code cannot assert it. If it is off, contestant IP addresses persist indefinitely — is that consistent with what the privacy page promises?
- **Which `LEADERBOARD_SOURCE` and `CTF_DATA_BACKEND` will actually be live during the event?** The weighting of T4 changes substantially between `lambda` (an ISR-cached fetch) and `dynamo` (a Query per contestant on every leaderboard view).
- **Is there a WAF, Vercel Firewall rule, or edge rate limit in front of the app?** Nothing in this tree throttles anything except the per-IP gate counter. If the answer is no, T4 is the top operational risk for the event.
- **What concurrent-viewer load is expected on `/leaderboard`, and what are the Upstash and DynamoDB capacity modes and spend caps?**
- **Who operates the scoring Lambda, is it in the same AWS account, and what is the trust relationship?** T11 assumes it is a third party from this app's perspective.
- **Is there an organizer runbook for mid-event incidents** — revoke one session, remove a team, roll back a score, disable hints — given every flag change requires a redeploy (T9)?
- **What is the disclosure path for a contestant who finds a bug in *this* app** rather than in the six targets? At a hacker conference with several thousand attendees this will happen; `SECURITY.md` is absent.
- **Is denial of service against the site itself in scope, or is availability a hard requirement for the three-day window?** This decides whether T4 and T6 are blockers or accepted risks.
- **Should the uncommitted working-tree changes ship before the event?** The auth hardening (`storeAccountCookie: false`, `disabledPaths`) is a genuine mitigation for T5 that is currently not deployed, and the new `/api/stats/visit` endpoint adds an unauthenticated write path (T4) that has not been through review.
